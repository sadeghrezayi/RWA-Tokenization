| 2026-07-31 | Onboarding ↔ KYC-queue semantics (2.3c/d) | **Assistant decision, flagged for review.** The wizard feeds the existing KYC state machine rather than duplicating it: submitting moves the investor `draft → submitted`; a resubmission after requested changes leaves an in-progress review alone (`in_review → submitted` is not a legal transition); an officer's *request changes* is NOT a KYC decision, so the case stays open in the officer's queue while the applicant fixes it. **Consequence to review:** an application waiting on the APPLICANT still appears in the officer's pending-KYC queue and the 1.8 ops work queue — the queue counts "open cases", not "waiting on us". If those should be separated, that is a queue-semantics change to scope. **Second flagged gap:** KYC `rejected` is terminal, so a rejected applicant cannot re-apply; resubmission is now refused explicitly instead of silently doing nothing — whether re-application should be possible is a product decision |
| 2026-07-31 | Onboarding step data + the old submit path (2.3e) | **(a) Provisional field set, encrypted** (user decision, assistant recommendation). Answers (name, national ID, address, bank account, suitability, agreement acceptance) are personal data and are stored **AES-256-GCM encrypted at rest**, erasable, exactly like the uploaded documents. **(b) The evidence-free KYC submit is REMOVED** (user decision, assistant recommendation): `POST /investors/me/kyc/submit`, its use case and the profile card's button are gone, so an application can no longer reach a reviewer with nothing attached; the six e2e suites that used it as a convenience now seed the queue state directly |
| 2026-08-01 | Portfolio analytics content (2.5a) | **Assistant decision, flagged.** The holder's portfolio is strictly FACTUAL and backward-looking: invested cost, current value from the latest ATTESTED valuation **carrying the date it was attested and a stale flag**, allocation share by value, and income that was actually PAID (a merely declared distribution is a promise, not income). There is deliberately **no projected yield, expected return or performance forecast** — OD-21 rules those out and nothing in the data would support them honestly. A derived "gain" figure is likewise not computed server-side; the components are given so a stale valuation can never be presented as a current profit. **Domain gap closed on the way:** a paid distribution recorded no date, so income could not be dated — `Distribution.markPaid(now)` and a nullable `paid_at` column were added. Rows paid before this migration have no date and are **excluded from the income statement** rather than shown undated |
| 2026-08-02 | OD-6 Payment rails | **Bank transfer confirmed by treasury** (user decision, assistant recommendation). Checkout spends the investor's internal Rial balance. Money-in: the investor declares an intended deposit and receives a unique payment reference (`TP-XXXXXXXX`, in an alphabet with no O/0, I/1/L or S/5 because a human types it into a bank form); they transfer; treasury finds the credit on a statement and confirms **the amount that actually arrived**, which is what reaches the ledger through the existing maker-checker credit (1.4b). No external contract, no third party, fits the self-hosted closed-loop posture, fully auditable. **Accepted costs:** funding takes hours or days, and someone must reconcile bank statements by hand. **The platform's own bank details are deployment configuration and REQUIRE LOCAL SETUP** — nothing in this codebase knows a real account |
| 2026-08-08 | Position detail — what one holding shows (2.5c) | **Assistant decision, flagged.** A holding opens onto its own page: tokens held, the value of THAT holding at the date it was attested (with a stale flag), what was invested in it, and what it has actually paid. It is a slice of the portfolio record the holder already has -- no new endpoint, no second definition of the same numbers. A position stays reachable after the tokens are gone: a fully redeemed holding still has the money that went in and the income that came out, and erasing that would erase the holder's own record. **What it deliberately omits:** anything forward-looking (OD-21), any derived gain figure (a stale valuation must never read as a current profit), and the asset's legal documents -- WHICH DOCUMENTS A HOLDER MAY SEE IS A PRODUCT AND LEGAL DECISION, not one to assume, so the documents centre named in the 2.5 roadmap line is NOT built. **Flagged:** an open (not yet closed) subscription shows allocated 0 and cost 0, which is true but does not show the money already held in escrow for it; the escrow figure lives on the Funds screen |
| 2026-08-08 | Checkout affordability + what an investor sees before committing (2.4e) | **Assistant decision, flagged.** The subscribe dialog is now a checkout step: it prices the order (tokens x price) as it is typed, shows the available balance and what is left after the order, and states that confirming HOLDS the money in escrow until the offering closes with unallocated funds returned. An order the balance cannot cover is refused CLIENT-SIDE with the exact shortfall and a link to the funding screen, so the ledger is never asked for a hold that must fail; the server's `InsufficientFundsError` remains the real guard and is still surfaced verbatim if it fires.
